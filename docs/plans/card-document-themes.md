# Themeable card documents (HTML)

> **Status:** Draft
> **Compatibility:** Extends the `.annot.html` v1 format from
> [`_done/annot-html-document.md`](./_done/annot-html-document.md)
> and builds on the card mechanics from
> [`_done/card-procedure-template.md`](./_done/card-procedure-template.md)
> and the auto-numbering badge from
> [`card-step-auto-numbering.md`](./card-step-auto-numbering.md).
> Splits the monolithic `injectDocumentStyles` into a fixed
> structural layer + a swappable theme layer. Adds a built-in
> theme registry, a `meta.appearance` opt-in, and a custom-CSS
> escape hatch. Touches `@ingcreators/annot-doc` (Tier A —
> structural vs theme CSS split, theme registry, sanitiser) and
> `@ingcreators/annot-host-ui` (Tier C — settings dialog, Storybook
> previews). The legacy `meta.theme` field stays for back-compat;
> the new `meta.appearance` takes precedence when set. Schema
> delta is additive — `data-annot-doc-version` stays at 1.
> **Risk:** Six phases, additive. Each phase lands as an
> independently revertable PR. The structural / theme CSS split
> in Phase 1 is the only invasive change; the rest is adding
> theme files and dialog surface.

## Context

The `.annot.html` document's appearance comes from a single
`<style>` block generated by `injectDocumentStyles` in
[`packages/doc/src/inject-styles.ts`](../../packages/doc/src/inject-styles.ts).
That function emits everything: CSS custom property values
(colours, fonts), structural rules (grid layouts, card chrome,
positioning), responsive behaviour, print rules, and theme
variants (light / dark / auto).

This works as a v1, but doesn't separate **what is structurally
load-bearing for the editor** (grid template, `[data-annot-block]`
selectors, the badge `::before` from
[`card-step-auto-numbering.md`](./card-step-auto-numbering.md))
from **what is cosmetic** (which colour, which font, which corner
radius, which shadow). The result:

- **Branding requires code changes.** A user wanting their
  company colours has to fork or override CSS post-export.
- **Variant designs are hidden.** "Modern Light" vs "Editorial
  Serif" vs "Brutalist Mono" are all reasonable choices for the
  same document content; today there's exactly one look.
- **Pairing with PPTX templates is impossible.** The PPTX-template
  plan ([`card-pptx-templates.md`](./card-pptx-templates.md))
  wants to share design tokens with the HTML side so a single
  "Appearance" choice carries through. Today the HTML side has
  no token concept exposed at the API.

This plan splits the CSS, introduces a small theme registry, and
adds an appearance picker. The output is still a single self-
contained `.annot.html` file — themes get inlined into the
`<style>` block at save time, no external dependencies.

## Design

### Structural vs theme CSS

The current `injectDocumentStyles` emits ~30 sections; some are
load-bearing for the editor, some are pure cosmetics. The split:

**Structural (always emitted, never overridden):**

- `[data-annot-block]` selectors (the editor's identification
  surface).
- Grid template definitions per `data-step-layout`.
- `position: relative` on step blocks, the inner image slot
  wrapper, and the badge `::before` (positioning anchors).
- Card-grid multi-column packing rules
  (`cardLayout.columns` handling).
- Print rules.
- `@media (max-width: 600px)` mobile collapse rules (modal
  fullscreen etc.).
- Counter declarations (`counter-reset` / `counter-increment`),
  but **not** the `::before { content }` rule — that's themable
  (theme controls badge shape + format).

**Themable (overridden per theme):**

- All `--annot-doc-*` and `--annot-card-*` CSS variable values
  (colours, max-width, card padding / radius / shadow).
- All `--annot-step-badge-*` values (badge bg / fg / radius /
  shadow, introduced by
  [`card-step-auto-numbering.md`](./card-step-auto-numbering.md)).
- Typography scale (font sizes for h1 / h2 / h3 / body /
  figcaption, line heights, letter spacing).
- Badge `::before` `content` template (lets `playful` theme
  render `"0N"`, `editorial` render `"N."`, etc.).
- Decorative borders / dividers between blocks.
- Optional theme-specific selectors (e.g. `editorial`'s pull-
  quote treatment via `[data-annot-block="quote"] {...}`).

### Data layer: `meta.appearance`

```ts
export interface DocMeta {
  // existing fields...
  theme?: "light" | "dark" | "auto";    // kept for back-compat
  // NEW
  appearance?: AppearanceMeta;
}

export interface AppearanceMeta {
  /** Built-in theme id, or "custom" when only customCss is set. */
  readonly template?: BuiltinThemeId | "custom";
  /** Free-form CSS appended after the chosen theme. Sanitised on
   *  parse — see "Custom CSS sanitisation" below. */
  readonly customCss?: string;
  /** Override the document's logical font tokens. Maps to the
   *  three tokens defined in `font-registry.ts`. */
  readonly fontFamily?: {
    sans?: string;   // logical token like "Annot Sans" or any CSS family
    serif?: string;
    mono?: string;
  };
}

export type BuiltinThemeId =
  | "modern-light"
  | "modern-dark"
  | "minimal"
  | "editorial"
  | "playful";
```

Precedence when both `meta.theme` and `meta.appearance.template`
are set: appearance wins. Legacy documents (no appearance field)
fall through to the existing `meta.theme` handling, which
implicitly maps to `modern-light` / `modern-dark` themes.

### Theme storage

Themes ship as **TypeScript modules** (not standalone `.css`
files) so they can use `cssStackFor("Annot Sans")` from
`@ingcreators/annot-core/headless` to interleave OS font stacks,
and so the build tree-shakes unused themes cleanly. Each module
exports:

```ts
// packages/doc/src/themes/modern-light.ts
import type { Theme } from "./types.js";

export const modernLight: Theme = {
  id: "modern-light",
  name: "Modern Light",
  description: "Soft shadows, blue accent, white background.",
  vars: {
    "--annot-doc-bg": "#ffffff",
    "--annot-doc-fg": "#1f2937",
    "--annot-doc-accent": "#2563eb",
    // ... all themable variables
    "--annot-step-badge-bg": "var(--annot-doc-accent)",
    "--annot-step-badge-fg": "#ffffff",
    "--annot-step-badge-radius": "50%",
    "--annot-step-badge-shadow": "0 4px 12px rgba(37, 99, 235, 0.25)",
  },
  darkVars: {
    "--annot-doc-bg": "#111827",
    "--annot-doc-fg": "#f9fafb",
    // ...
  },
  extraCss: "",  // optional theme-specific selectors
  badgeLabelTemplate: "%n",  // CSS content template for the step badge
};
```

Light + optional dark variants come paired. When the chosen
theme has both, the dark variant lives behind `@media
(prefers-color-scheme: dark)`. Themes that are exclusively
light or exclusively dark omit the matching half.

### Built-in themes (Phase 2)

| ID | Design intent |
|---|---|
| `modern-light` (default) | Current look, refined. Soft shadows, blue accent, neutral typography. |
| `modern-dark` | Dark-mode-only variant — neon-leaning accent for contrast. |
| `minimal` | No shadows, hairline borders only, mono-toned palette. Tight typography. |
| `editorial` | Serif headings (`Annot Serif`), generous line-height, magazine-style block treatment, pull-quote styling. |
| `playful` | Pastel palette, larger radii, badge as a chat-bubble shape, oversize typography. |

Five is a reasonable starting set covering the visual axes
(formal vs casual, light vs dark, dense vs spacious). The plan
deliberately stops short of "20 themes" — quality per theme
matters more than count.

### Custom CSS

Power users can supply free-form CSS via `meta.appearance.customCss`.
It's appended **after** the theme CSS so it can override anything.

Sanitisation on parse + save:

- Reject any `@import` rules (no external loading).
- Strip `url(http://...)` and `url(https://...)` references —
  prevents tracking pixels embedded as background images. Allow
  `data:` URLs. (Replaceable with a warning + opt-in later, but
  default to safe.)
- Reject any `behavior: url()` legacy IE constructs.
- Cap total length at 8 KB to prevent saved-file bloat.

Implemented as a Tier A function in `packages/doc/src/themes/sanitise-custom-css.ts`,
called from the parser and from the dialog's save action.

### Font family override

`meta.appearance.fontFamily` maps to the existing logical font
tokens system (`packages/core/src/editor/font-registry.ts`).
When set:

- `sans` overrides `--annot-doc-font-sans` (the default
  body / heading family).
- `serif` overrides `--annot-doc-font-serif` (used by the
  `editorial` theme).
- `mono` overrides `--annot-doc-font-mono` (code blocks).

Values are passed through `coerceToLogicalFamily()` when they
match a known token, otherwise treated as a raw CSS family stack
(power users can paste `"Helvetica Neue, sans-serif"`).

### CSS generation pipeline

```ts
function injectDocumentStyles(doc: AnnotDocument): AnnotDocument {
  const themeId = doc.meta.appearance?.template ?? legacyThemeFallback(doc.meta.theme);
  const theme = THEMES[themeId] ?? THEMES["modern-light"];

  const parts = [
    structuralCss(doc),                              // unchanged across themes
    themeCss(theme, doc),                            // vars + extraCss
    fontOverrideCss(doc.meta.appearance?.fontFamily),
    sanitiseCustomCss(doc.meta.appearance?.customCss ?? ""),
  ];

  return { ...doc, styleBlock: parts.filter(Boolean).join("\n") };
}
```

`structuralCss(doc)` is the new home for the section-by-section
logic currently in `injectDocumentStyles`, minus everything that
moved into theme tokens. `themeCss(theme, doc)` emits:

```css
:root {
  --annot-doc-bg: #ffffff;
  --annot-doc-fg: #1f2937;
  /* ...all light vars... */
}
@media (prefers-color-scheme: dark) {
  :root {
    --annot-doc-bg: #111827;
    /* ...all dark vars... */
  }
}
/* extraCss, if any */
[data-annot-block="step"]::before {
  content: <parsed badgeLabelTemplate>;
}
```

### Settings dialog: Appearance tab

The doc-settings dialog gains a new "Appearance" tab (alongside
existing General / Numbering tabs). It shows:

- Theme picker — radio cards with thumbnail previews of each
  built-in theme. Selecting one writes
  `meta.appearance.template`.
- Font family override — three text inputs (sans / serif / mono)
  with placeholder text showing the default token.
- "Advanced: Custom CSS" expander — a textarea with the saved
  customCss, sanitisation warnings inline ("Removed 2 external
  url() references for safety").

Selecting a theme triggers a fresh `injectDocumentStyles` →
`styleBlock` rewrite → editor re-render. Live preview.

### Editor view parity

`<annot-doc-shell>` reads `doc.styleBlock` and applies it. No
shell-side change is needed; themes flow through the existing
CSS injection.

Storybook gets a new top-level group: `Document / Themes / *`
with one story per built-in theme, showing the same sample
document rendered five different ways.

## Phased plan

One PR per phase, each independently revertable.

### Phase 1 — Structural / theme CSS split

- Refactor `injectDocumentStyles` into `structuralCss(doc)` +
  `themeCss(theme, doc)`. No new themes yet — the only existing
  "theme" stays inline, equivalent to today's output.
- Extract themable CSS variables into a single Tier A `Theme`
  type ([`packages/doc/src/themes/types.ts`](../../packages/doc/src/themes/)).
- Define the initial `modern-light` and `modern-dark` themes
  matching today's `meta.theme === "light"` / `"dark"` outputs
  byte-for-byte. The `auto` legacy value maps to "use
  `modern-light` vars + `prefers-color-scheme: dark` overrides".
- Goldens: round-trip every existing `.annot.html` fixture
  through the new pipeline; bytes must be identical.

**Verified:** existing `inject-styles.test.ts` snapshots
unchanged; new `themes.test.ts` confirms each theme's CSS
production.

### Phase 2 — Built-in theme registry + three new themes

- Add `minimal`, `editorial`, `playful` themes to the registry.
- `BuiltinThemeId` enum + `THEMES` lookup in
  [`packages/doc/src/themes/index.ts`](../../packages/doc/src/themes/).
- `meta.appearance.template` is parsed / serialised (Tier A);
  takes precedence over `meta.theme` when set.
- Storybook: `Document / Themes / *` showing each theme.

**Verified:** typecheck + lint + Storybook visual review. No
behavioural change for documents without `meta.appearance`.

### Phase 3 — Settings dialog Appearance tab

- New tab in [`doc-settings-dialog.ts`](../../packages/host-ui/src/ui/doc-settings-dialog.ts).
- Theme picker as a list of radio cards. Live preview when the
  user selects a theme (writes to DocumentHistory; undo restores).
- "General" tab's existing `Theme: Light / Dark / Auto` control
  stays for back-compat, marked "(Legacy)". Selecting a value
  here clears `meta.appearance.template` so the legacy field
  wins.
- Story for the dialog showing the new tab.

**Verified:** manual test cycling through every theme; verifying
the editor + save-on-disk byte snapshot updates.

### Phase 4 — Font family override

- `fontFamily` field parsed / serialised (Tier A).
- `fontOverrideCss()` generator emits `:root { --annot-doc-font-sans: ...; }`
  when set.
- Three text inputs in the Appearance tab. Logical token
  values get coerced; raw families pass through.
- Round-trip tests cover all token combinations.

**Verified:** PNG raster of an edited doc (via the
existing rasterisation path) shows the override font.

### Phase 5 — Custom CSS escape hatch

- `customCss` field parsed / serialised (Tier A).
- `sanitiseCustomCss()` Tier A helper with the rules from
  the Design section.
- "Advanced: Custom CSS" expander in the Appearance tab. Inline
  warnings list any rules that got stripped.
- 8 KB length cap surfaced as a soft warning in the dialog
  ("Your CSS is X KB / 8 KB max") + hard cap on save (truncate
  with toast).

**Verified:** sanitiser unit tests cover every reject branch;
manual paste of malicious CSS into the dialog confirms strip
+ warning.

### Phase 6 — Plugin docs + format reference + archival

- Update [`docs/annot-html-format.md`](../../docs/annot-html-format.md)
  to document `meta.appearance` (and its fields).
- New doc: [`docs/plugin-api/themes.md`](../../docs/plugin-api/themes.md)
  describing the `Theme` shape for plugin-supplied themes
  (Phase 7 enabler — out of scope, but the type is the public
  surface either way).
- CLAUDE.md guardrails get a new section #11 covering the
  structural / theme split invariant: anything the editor's DOM
  walks for must stay structural, never themable.
- Plan moves to `_done/`.

**Verified:** docs build with `pnpm --filter @ingcreators/annot-web build`.

## Migration notes

- Schema delta is additive. `data-annot-doc-version` stays at 1.
- Documents with `meta.theme` set keep working. The new code
  path maps `theme === "light"` → `modern-light`, `"dark"` →
  `modern-dark`, `"auto"` → `modern-light` (which carries the
  `prefers-color-scheme: dark` branch internally).
- Documents without `meta.appearance` continue to use the
  legacy mapping — no implicit migration to the new field. The
  user opts in by selecting a theme in the dialog.
- The Appearance dialog explicitly clears `meta.theme` when the
  user picks a new appearance template (so the legacy + new
  fields don't fight). The reverse is also true — picking the
  "Legacy" theme dropdown clears `meta.appearance.template`.

## Forward-looking notes

- **Plugin-supplied themes.** Phase 6's `Theme` type doc is the
  groundwork. A future plan extends `PluginHost` with a
  `addTheme(theme: Theme)` API; plugin themes appear in the
  Appearance picker alongside built-ins.
- **Pairing with PPTX templates.** Each built-in theme will gain
  a matching PPTX template (same colours, same typography
  spirit) in [`card-pptx-templates.md`](./card-pptx-templates.md).
  The Appearance picker becomes the single source of truth for
  "how this document looks" across HTML + PPTX surfaces.
- **Theme editor UI.** Out of scope. A future plan could add a
  visual editor for tuning a custom theme without writing CSS.
- **CSS-counter step badge** lives in
  [`card-step-auto-numbering.md`](./card-step-auto-numbering.md);
  this plan is what makes the badge's visual style customisable
  per theme.
