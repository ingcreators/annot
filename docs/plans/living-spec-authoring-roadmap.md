# Living-spec visual authoring roadmap

> **Status:** In progress — Phase 1 implementation started 2026-05-23.
> Original plan body below was written 2026-05-22 as the synthesis of a long
> design discussion that started from
> [`playwright-screenshot-fixture-relayer.md`](./_done/playwright-screenshot-fixture-relayer.md)'s
> Q&A about Playwright codegen compatibility and walked through six
> architectural alternatives before landing on a 3-layer model.
>
> **Trigger:** The relayer plan's review surfaced that
> `@ingcreators/annot-product-docs-astro/playwright`'s
> `page.screenshot({ annot: { mdx } })` patch is not actually
> Astro-specific. That observation cascaded into a re-examination
> of how the whole living-product-docs surface is layered, and
> revealed that the editor → MDX → PNG triangle is currently
> ambiguous about who owns what. This roadmap captures the
> resulting positioning decision: **Annot becomes the visual
> authoring surface for living product docs**, with a strict
> 3-layer artifact model and an 8-phase implementation path
> that ends with embedded in-browser editing committing back
> to GitHub (Phase 5), a host-neutral MDX WYSIWYG editor
> surface (`<annot-mdx-editor>`, MDXEditor-based) that lets
> non-IDE users edit both annotation yaml (via image-click
> modal) and `<AnnotCallout>` bodies (via AST-stable
> rich-markdown round-trip) from one place (Phase 6), a single
> self-contained HTML distribution adapter (Phase 7), and the
> unification of card-style docs with screen-spec docs onto a
> single MDX authoring path (Phase 8, includes the destructive
> removal of the unpublished `@ingcreators/annot-doc` package).
>
> **Compatibility:** Additive throughout. Existing `<Overlay>` JSX
> migrates to the new `<AnnotCallout>` form via deterministic
> CLIs (legacy `<Overlay>` is the pre-Phase-2 name; the new form
> uses the `Annot` prefix per AD-14). Existing `screen.capture(...)`
> stays as a documented escape hatch. The PNG XMP format gains
> new optional fields. No `data-annot-version` bump.
>
> **Risk:** Medium. Each phase is independently shippable; the
> architectural commitments are well-reasoned but cover a lot of
> surface. Phase 5 (embedded editor + GitHub round-trip) lives
> partially in `annot-cloud` (private repo) and depends on the
> annot-cloud auth foundation in
> [`annot-cloud-roadmap.md`](./annot-cloud-roadmap.md) Phase 3.

## TL;DR

After
[`_done/living-product-docs.md`](./_done/living-product-docs.md)
landed the docs platform (MDX + Playwright fixture + Astro
adapter + Excel adapter), one foundational question stayed open:
**how do people without IDE access edit living-product-docs?**
Today the answer is "open the MDX file in VSCode, type JSX." This
roadmap replaces that with: open the PNG in Annot, click an
element, type text, save. Either locally (Annot desktop /
VSCode), in a hosted editor (annot.work/app), or — as the
terminal ambition — **inline inside the rendered docs site
itself, with edits committing back to GitHub**.

The journey requires re-thinking the artifact model. Today's
`<Overlay match={...} intent number>text</Overlay>` JSX (the
legacy pre-Phase-2 form) conflates **three different things**
with three different lifecycles:

| Concern | Lifecycle | Editor | Today's home |
|---|---|---|---|
| Image + aria-snapshot | Re-captured on UI change | Playwright tour | PNG + MDX `annot:snapshot` block |
| Visual annotation (numbered badge / arrow / rect / etc.) | Edited when "what to point at" changes | Annot editor (proposed) | `<Overlay>` JSX `match` / `intent` / `number` props |
| Description text | Edited per-audience, translated per-language | Technical writer / PM | `<Overlay>` JSX children |

The roadmap separates these into three layers, each with its
own storage and editor:

- **Layer 1**: PNG with `annot:snapshot` / `annot:attributes` in XMP. Machine-generated by Playwright, regenerated on re-capture.
- **Layer 2**: `.annotations.yaml` files referenced from MDX via `<AnnotFigure annotations="...">`. Machine-resolvable (each entry has `match: { role, name }` or free coords). Edited via Annot editor's new Overlay tool.
- **Layer 3**: `<AnnotCallout for="id">text</AnnotCallout>` JSX inside MDX. Rich markdown / JSX content, per-audience, translatable. Edited in any MDX editor.

This separation enables:

1. **Annot stays a general PNG annotator** — the docs use case is one of many.
2. **MDX retains markdown / JSX expressiveness** for description body.
3. **PNG is re-capture-safe** — overlays don't live in PNG, so overwriting PNG doesn't destroy human work.
4. **Multi-book / multi-audience** — same PNG + annotation yaml, different MDX descriptions.
5. **Embedded editing** — annot.work iframe can mount in any docs page and round-trip edits via GitHub Storage.

## Strategic positioning

Today's competitive landscape:

| Product | Visual editor | Docs output | Embedded editing | Enterprise (SSO / on-prem / audit) |
|---|---|---|---|---|
| VitePress / Mintlify | None (markdown only) | Yes | None (PRs only) | Mintlify Pro |
| Notion | Rich text | Yes | Yes (in-app, not git) | Notion Enterprise |
| Confluence | Rich text | Yes | Yes (in-app, not git) | Atlassian Cloud / DC |
| Excalidraw | Free-form drawing | Limited | Limited | None |
| Figma | UI design | Read-only | Comments only | Figma Enterprise |
| **Annot (after this roadmap)** | **Element-aware visual** | **Yes** | **Yes (git-backed)** | **On-prem `cloudUrl` + SSO** |

The combination — visual editor + element-aware annotations + git
round-trip — has no existing competitor. Mintlify is closest but
lacks visual editing; Notion is closest on UX but isn't
git-backed. Enterprise tier additionally differentiates on
**on-prem deployability** (the `<AnnotEditButton cloudUrl>` config
lets the same OSS component point at customer infrastructure)
plus SSO via SAML / Okta / Azure AD — a combination Notion /
Confluence offer but Mintlify and Excalidraw don't.

The default embed mode (`newTab`, see OQ-09) was chosen
specifically to keep this Enterprise compatibility intact
without forcing the consumer / Pro tier to give up smooth UX
(`inline` iframe mode opt-in remains available for those
deployments).

This positions Annot as **the canonical editor for screen
specifications** (画面仕様書) — a category that exists in
Japanese enterprise tech especially heavily (operation manuals,
screen design documents, regression-test specs), and that
currently lives in Excel / PowerPoint / Confluence with no
modern tooling.

The OSS / Cloud split per
[`oss-cloud-split.md`](./oss-cloud-split.md):

- **OSS** (`annot` repo): Annot editor + product-docs core +
  Astro adapter + Excel adapter + annotation yaml format + local
  filesystem / GitHub storage
- **annot-cloud** (private repo): hosted editor at `annot.work/app/`,
  iframe embed mode, GitHub App for server-side commits, build
  trigger integration, multi-tenant DB, billing

Phase 5 of this roadmap straddles both repos.

### Why three layers, not one or two

The 6 alternatives considered during the design discussion (and
why each fails) are captured in
[Discarded alternatives](#discarded-alternatives) at the bottom.
The short version:

- **One file (PNG with everything)**: re-capture overwrites PNG, destroying human overlays.
- **Two files with PNG sidecar (`.overlays.yaml` paired with PNG by filename)**: pair fragility — move PNG without yaml, data lost.
- **Two files with MDX inline (current state)**: requires MDX JSX writer for the editor (highest implementation cost), conflates structure/text concerns.
- **Three files (this proposal)**: explicit link in MDX prevents pair fragility, separation of concerns is clean, no MDX JSX writer needed.

The third layer (Description in MDX) is non-negotiable per the
user's feedback during the session: description text wants
markdown formatting, inline JSX components (`<code>`,
`<KeyboardKey>`, `<Note>`, etc.), and integration with existing
translation pipelines. YAML for description is over-extraction.

### Why annotation yaml is referenced explicitly, not paired by filename

```mdx
<AnnotFigure
  src="../shots/login.png"
  annotations="../annotations/login.annotations.yaml"  ← explicit
/>
```

The `annotations` prop is non-optional once Layer 2 is in use.
If MDX moves, the prop's relative path needs updating just like
`src`. If the yaml file goes missing, **the Astro build fails
loudly** instead of silently rendering without overlays.

Pairing by filename convention (e.g. `login.png` →
`login.overlays.yaml` in same dir) was rejected because:

1. **File moves break silently**: `mv login.png shots/old/` doesn't bring the sidecar.
2. **Sharing strips the pair**: PNG dropped into Slack / email arrives without yaml.
3. **No build-time validation**: missing yaml silently degrades to "no overlays" output.

Explicit reference makes the link a first-class MDX dependency,
verifiable at build time and visible in code review.

### How the editor never touches MDX

A central simplification: **Annot editor's save flow writes only
the annotation yaml**. Never the MDX. Never the PNG XMP (except
for tour-generated snapshot data, which the editor itself
doesn't write).

This eliminates the MDX JSX writer that earlier iterations of
this design required. MDX JSX is **read-only** to the editor —
the editor opens MDX to discover linked yaml paths, then edits
the yaml.

Editor implementation surface shrinks dramatically:

| Capability | Implementation |
|---|---|
| Read PNG XMP snapshot | Existing `@ingcreators/annot-core/xmp-bytes` |
| Display snapshot regions as clickable | New (parses YAML → Lit overlay component) |
| Add / move / edit annotation | New (modifies in-memory yaml model) |
| Save annotation yaml | New (Tier A YAML serializer, ~50 lines) |
| Open via MDX context | New (MDX → `<AnnotFigure annotations>` lookup) |
| Direct PNG open | New (no MDX context, no edit; read-only) |

**No remark-mdx walking, no JSX node insertion, no byte-stable
markdown rewriter.**

### Annotation type palette

Layer 2 yaml accommodates Annot's full annotation palette, not
just numbered badges:

```yaml
version: 1

overlays:
  # numbered callouts (the docs-primary use case, matches today's <Overlay>)
  - id: o1
    kind: numberedBadge
    match: { role: "textbox", name: "Email" }
    intent: required
    number: 1

annotations:
  # arrows between elements
  - id: a1
    kind: arrow
    from: { match: { role: "button", name: "Sign in" } }
    to:   { match: { role: "main" } }
    intent: action

  # rect bounding multiple elements
  - id: a2
    kind: rect
    coversElements:
      - { match: { role: "textbox", name: "Email" } }
      - { match: { role: "textbox", name: "Password" } }
    intent: info

  # text annotation anchored to element
  - id: a3
    kind: text
    anchor: { match: { role: "heading", name: "Sign in" }, position: above }
    text: 未認証ユーザのエントリポイント

  # free-form annotations (UI changes may misalign these)
  - id: a4
    kind: freehand
    path: "M100,200 L150,250 L200,210"
    stroke: "#ff0000"

  - id: a5
    kind: redact
    bbox: { x: 421, y: 269, width: 438, height: 40 }
    style: solid

  - id: a6
    kind: focusMask
    cutout: { match: { role: "button", name: "Sign in" }, padding: 8 }
    intent: action
```

Two top-level sections:

- `overlays[]` — numbered badges, the docs-primary numbered-callout case. Always match-anchored. Has `text` if Description is inline (transition state during migration), or has `description: false` to signal "no description, just a numbered marker."
- `annotations[]` — everything else: arrows, rects, text labels on the image, freehand, redact, focus mask, etc. May be match-anchored, may be free-coord.

The split is by **whether the docs flow renders a description
slot for it**. `overlays[]` entries get a description rendered
below the image; `annotations[]` entries are pure visual marking
with no description slot (though they can carry an `intent` for
styling).

`<AnnotCallout for="id">` JSX in MDX targets `overlays[]` IDs.
`annotations[]` IDs are never referenced from MDX — they're
self-contained visual marking.

### Match resolution and drift

Both `match: { role, name }` and free-coord (`bbox` / `position`
/ `path`) are supported. Match-anchored entries:

- Survive UI layout changes (the snapshot resolver picks them up by role+name)
- Subject to drift detection (`annot-docs lint` flags missing matches)
- Coordinates computed at build time from snapshot's `[box=...]` markers

Free-coord entries:

- Immune to drift detection (no match to verify)
- Brittle to UI changes (pixel coordinates don't track layout)
- Used for decorative annotations, freehand sketches, redact regions

Element-anchoring is the preferred default. Annot editor's UI
nudges users toward it: dragging an annotation near a snapshot
element offers a "snap to element" affordance that converts
free-coord to `match`-based.

### Phase 0 — Architecture relayer (Draft)

Already captured in
[`playwright-screenshot-fixture-relayer.md`](./_done/playwright-screenshot-fixture-relayer.md)
([PR #955](https://github.com/ingcreators/annot/pull/955)).

Moves `page.screenshot({ annot: { … } })` prototype patch from
`@ingcreators/annot-product-docs-astro/playwright` to its proper

- `@ingcreators/annot-product-docs` extends the registry with the `mdx` resolver

for a multi-phase evolution.

### Phase 1 — Unified `ElementTree` data model + PNG XMP storage

**Goal**: Introduce a single source-agnostic `ElementTree` type
as the canonical representation of "what's on this page",
replacing both today's parallel paths (extension's
`PageMetadata` flat list, Playwright's `ariaSnapshot` YAML +
`annot:attributes` block). Stored in PNG XMP as a single
`annot:elementTree` payload. Consumed uniformly by editor /
Astro / drift detector / MCP tools.

**Why this scope**: Earlier draft of this roadmap planned to
cache the raw Playwright YAML and the attributes YAML
separately in PNG XMP (mirroring the existing MDX comment
blocks). Subsequent design discussion surfaced that the
extension's `PageMetadata` and Playwright's snapshot are
**conceptually the same data with different shapes**, kept
apart by implementation accident. With the extension's schema
breakable (`PageMetadata` is acknowledged "first cut"),
Phase 1's right scope is to converge both paths onto a single
canonical model, eliminating the duplication at the root.

#### Canonical schema

`@ingcreators/annot-core/element-tree` (Tier A, new):

```ts
export interface ElementTree {
  version: 1;
  source: {
    kind: "extension" | "playwright" | (string & {});
    capturedAt: string;          // ISO 8601
    agent?: string;               // tool name + version
    url?: string;                 // captured page URL
  };
  viewport: {
    width: number;                // CSS px
    height: number;
    scale: number;                // devicePixelRatio
  };
  root: ElementNode;
}

export interface ElementNode {
  /** ARIA role. Always present — decorative nodes use "generic" or "presentation". */
  role: string;
  /** Accessible name. */
  name?: string;
  /** Page-space bounding box in CSS px. Omitted for hidden/abstract nodes. */
  bbox?: BBox;
  /** Tree-unique identifier, `e<n>` format (depth-first numbering).
   *  Stable within one capture; not stable across re-captures (see OQ-11). */
  ref: string;
  /** ARIA states (single tokens): "checked" / "pressed" / "expanded" /
   *  "selected" / "disabled" / "required" / "invalid" / "level=2" /
   *  "valuetext=10" / etc. */
  states?: readonly string[];
  /** HTML attribute snapshot (whitelist-filtered at capture time). */
  attributes?: Readonly<Record<string, string>>;
  /** Direct text content (heading body, paragraph text, textbox value).
   *  Distinct from `name` for elements where they differ. */
  text?: string;
  /** Children in document order. */
  children?: readonly ElementNode[];
}

export interface BBox { x: number; y: number; width: number; height: number; }
```

#### Verification

- **Schema round-trip**: any ElementTree serializes to YAML / JSON and parses back to byte-identical structure
- **Playwright adapter parity**: an existing Playwright snapshot YAML (e.g. from workflow-app fixtures) converts to ElementTree and back to byte-equivalent YAML
- **Extension adapter parity**: an extension capture on a known fixture page produces an ElementTree with the same elements as today's `PageMetadata` (modulo ordering — tree vs flat)
- **Migration CLI**: workflow-app's 17 MDX files migrate cleanly. PNG bytes change (XMP added) but Astro builds produce identical visual output
- **Drift detector**: unified detector reports the same findings as today's two separate detectors on the same fixtures

#### Out of scope for Phase 1

- Cross-capture `ref` stability (refs are transient per capture). Tracked in OQ-11.
- Locator field for Playwright extension handoff (P5's old `locator?: string` aspiration). Reserved for future phase if Playwright integration in editor needs it.
- Attribute whitelist per role (e.g. only collect `type/required/maxlength` on `textbox`, only `href` on `link`). Phase 1 keeps the global whitelist; per-role whitelisting is a Phase 2 follow-up if collection size becomes a problem.

### Phase 2 — Annotation yaml extraction + `<AnnotCallout>` JSX

**Goal**: Move `match` / `intent` / `number` from the legacy
`<Overlay>` JSX props into `.annotations.yaml` files. Replace
the legacy `<Overlay>` JSX with the new
`<AnnotCallout for="id">body</AnnotCallout>` (the AnnotXxx-prefixed

### Phase 5 — Embedded editor + GitHub round-trip

**Goal**: Annot editor reachable from any docs site via an
`<AnnotEditButton>` component, edits commit back to GitHub via
annot-cloud's GitHub App integration. The button supports
multiple **embed modes** so the same OSS component fits
consumer / Pro / Team / Enterprise deployment scenarios.

#### Embed modes

The `<AnnotEditButton>` component supports three modes, selected
either per-call (`mode` prop) or globally via
`annot-docs.config.ts`:

| Mode | UX | Best for | Trade-off |
|---|---|---|---|
| **`newTab`** (default) | Click → new tab opens annot-cloud editor → edit → tab closes / returns | Enterprise / Team / Air-gapped (with on-prem `cloudUrl`) | Tab switching friction, but rock-solid SSO / CSP / on-prem compatibility |
| **`inline`** (opt-in) | Click → modal iframe loads annot-cloud editor → edit → modal dismisses | Consumer / Pro / personal sites | Smooth UX but requires CSP `frame-src` whitelist + third-party cookie support |
| **`disabled`** | Button not rendered | Pure-static read-only sites / air-gapped without on-prem cloud | No edit affordance shown |

Configuration:

```ts
// annot-docs.config.ts
export default defineConfig({
  editor: {
    embedMode: "newTab",                  // "newTab" (default) | "inline" | "disabled"
    cloudUrl: "https://annot.work",       // override with "https://annot.example.com" for on-prem
  },
});
```

```mdx
{/* Global default (newTab) */}
<AnnotEditButton repo="..." path="..." />

{/* Per-call opt-in to inline iframe */}
<AnnotEditButton repo="..." path="..." mode="inline" />

{/* Per-call disable (e.g. on a frozen reference page) */}
<AnnotEditButton repo="..." path="..." mode="disabled" />
```

The `newTab` default is the **architecturally safer choice**
because it works under every Enterprise constraint
(strict CSPs, SSO redirect flows, on-prem deployments,
third-party cookie bans, network isolation with an internal
annot-cloud instance). The `inline` mode is a UX upgrade for
consumer-grade deployments where those constraints don't
apply.

#### Files added (annot repo, OSS side)

- `packages/product-docs-astro/src/components/AnnotEditButton.astro` — MDX-mountable component. Renders an "✏️ Edit" button. Resolves embed mode from per-call `mode` prop OR `annot-docs.config.ts` `editor.embedMode`. Opens `${cloudUrl}/embed?repo=...&path=...&return=...` in new tab (default) or iframe modal (opt-in).
- `packages/product-docs-astro/src/components/AnnotEditorIframeModal.astro` — modal wrapper for `mode: "inline"`. Lazy-loaded so `mode: "newTab"` sites don't ship the modal code.
- `packages/annot-embed-protocol/` (new workspace package) — Tier A. Defines the protocol between docs site and editor in BOTH modes: postMessage events (for inline iframe) AND URL-callback events (for newTab, via `?return=https://docs.site/path#edit-complete=<edit-id>` redirect). Messages: `EditorReady` / `EditRequested` / `EditCommitted` / `EditAbandoned` / `ResizeNeeded`.

#### Files added (annot-cloud repo, paid side)

- `embed/` route in annot-cloud — receives URL params (`repo` / `pngPath` / `annotationsPath` / `return`), reads from GitHub via GitHub App credentials, mounts an editor instance. On commit:
  - `mode=inline`: sends `EditCommitted` postMessage to parent
  - `mode=newTab`: redirects to `${return}?edit-complete=<edit-id>` so docs site picks up the result
- GitHub App "annot-cloud-editor" — installable on customer repos. Permissions: contents (read+write), metadata (read), pull_requests (write, for PR-mode edits).
- Worker route in annot-cloud Workers that proxies the GitHub commit (so the editor doesn't need a user PAT — only the GitHub App's installation token).
- Build trigger integration — after commit, the Worker pings the customer's Cloudflare Pages / Vercel / GitHub Pages build endpoint (configured per-installation).
- **On-prem variant**: annot-cloud bundle deployable to customer infrastructure. Same `embed/` route, same GitHub App registration model, but served at customer subdomain. Customer's `<AnnotEditButton cloudUrl="https://annot.internal.example.com">` points there.

#### UX flow (default `newTab` mode)

```
Public docs site (annot.work/docs or customer site)
  ↓
Visitor sees <AnnotFigure> with annotated PNG + descriptions
  ↓
"✏️ Edit" button (only if AnnotEditButton component present + repo has annot-cloud App installed + embedMode != "disabled")
  ↓
Click → window.open("${cloudUrl}/embed?repo=...&path=...&return=https://docs.site/login#edit-complete")
  ↓
New tab loads annot-cloud editor; visitor authenticates if not already signed in (SSO / GitHub OAuth — works natively since no iframe)
  ↓
Editor loads PNG + yaml from GitHub via GitHub App
  ↓
User edits visual annotations
  ↓
"Save" → annot-cloud commits to GitHub (PR or direct push per installation policy)
  ↓
Tab redirects to return URL with edit-complete hash
  ↓
Original docs tab (still open) picks up the hash on focus, shows "Edit saved, site rebuilds in ~1 minute" toast
  ↓
Build trigger fires → site rebuilds in 30s-2min → user refreshes
```

#### UX flow (opt-in `inline` mode)

```

  ↓

  ↓
```

- **Signed-in viewer without repo write**: editor opens in read-only mode (still useful for previewing annotations) + offers "Suggest changes via PR" flow

### Phase 6 — `.annot.mdx` unified authoring surface

**Goal**: A single Annot-hosted MDX editor surface where the
rendered MDX is WYSIWYG-editable, image blocks open the existing
annotation editor in a modal (mirroring the card-document
`<annot-doc-image-editor-modal>` pattern from
[`_done/card-document-themes.md`](./_done/card-document-themes.md)),
and Description bodies + surrounding markdown are edited
in-place with AST-level round-trip. Three distinct layers, three
distinct writers, one editor:

- **Image click → annotation editor modal** writes Layer 2 (annotation yaml). Reuses Phase 4's writer wholesale.
- **`<AnnotCallout>` body edit** writes Layer 3 (MDX) via MDXEditor's AST round-trip — only the inner markdown of the `<AnnotCallout>` block changes, the `<AnnotCallout for="…">` JSX structure stays byte-stable.
- **Surrounding markdown edit** writes Layer 3 (MDX) the same way — paragraphs / headings / lists round-trip through the AST.

The surface lands first as a VSCode custom editor registered
for `.annot.mdx` (extending the existing `.annot.{svg,png,jpeg,jpg}`
registration), with annot.work/app and Annot desktop following
the same `<annot-mdx-editor>` Lit component.

**Why this scope**: Phase 4 + 5 deliver visual annotation
editing through the AnnotEditButton flow, but callout body
editing still requires an IDE. Phase 6 closes the last gap —
non-IDE users edit both Layer 2 (yaml) and Layer 3 (MDX
descriptions) from one surface. The technical breakthrough
that makes this safe (and overturns DA-03's prior rejection)
is **MDXEditor**: an MDX-native WYSIWYG built on Lexical that
treats unknown JSX as opaque AST nodes with byte-stable
round-trip. There is no "synthesize JSX from canvas operation"
path — MDXEditor edits the MDX directly the way a user types
into a text editor, just with WYSIWYG presentation. DA-03's
fatal flaw (byte-stable JSX writer for canvas-driven overlay
insertion) does not apply here.

#### MDXEditor selection rationale

See [AD-11](#ad-11-mdxeditor-chosen-over-tiptap-lexical-raw-prosemirror-raw-codemirror-split-view)
for the full comparison. Short version: MDXEditor
([mdxeditor.dev](https://mdxeditor.dev)) is the only candidate
that's MDX-first (not markdown-with-patches), preserves unknown
JSX byte-stable, allows registered components to render with
custom WYSIWYG renderers, and supports frontmatter + imports
out of the box. The single trade-off is React, captured in
[AD-10](#ad-10-react-permitted-inside-annot-mdx-editor-boundary-lit-elsewhere).

### Phase 7 — Single-HTML distribution adapter

**Goal**: A new `@ingcreators/annot-product-docs-html` adapter
that emits **self-contained single .html files** from MDX
sources. Two output modes: (a) single MDX → single HTML
(distribution unit = one page), (b) multi-MDX book → single
HTML book with client-side router + TOC (distribution unit =
one signed-off operation manual / screen specification book).
Both modes inline every asset (PNG as data URI, CSS in
`<style>`, optional JS for router + interactivity) so the
output ships as one file via email / Slack / USB / shared
drive without any IT involvement.

**Why this scope**: Phase 5 + 6 deliver editing flows, but the
*distribution* end of the docs value chain still routes
through an Astro static site (multi-page, multi-file). Japanese
enterprise tech consumers — the primary target for
画面仕様書 (screen specifications) and 操作マニュアル
(operation manuals) — expect the deliverable as a single
self-contained file they can attach to email or copy to a
shared drive. Phase 7 closes that gap. Combined with Phase 5's
`<AnnotEditButton>`, the distributed HTML stays editable:
recipients open the HTML, click Edit → new tab opens
annot-cloud editor → commit → site rebuilds → distributor
re-sends the updated HTML.

## Architectural decisions

### AD-01: Annotation yaml is referenced explicitly from MDX, not paired by filename

Pairing breaks under filesystem operations (move / rename /
copy). Explicit `annotations="..."` prop in `<AnnotFigure>` makes
the dependency:

- **Visible** in code review
- **Verifiable** at build time (missing file → Astro build error)
- **Editable** as a normal MDX attribute when files move
- **Lintable** via `annot-docs lint`

### AD-02: Callout body lives in MDX, not yaml

YAML can't natively express:

- Markdown formatting (bold, italic, code, lists, links)
- Inline JSX (`<Link>`, custom Annot-prefixed components, etc.)
- Multi-paragraph structure with semantic markup

MDX is the right home for `<AnnotCallout>` body content.
The canvas editor (Phase 4) never touches MDX — callout body
editing happens in the MDX editor (Phase 6), in any IDE, or
via the embedded editor flow (Phase 5+6 combined).

### AD-03: PNG carries snapshot, not overlays

Snapshot is re-generated on every Playwright tour. PNG is
overwritten on re-capture. If overlays lived in PNG, they'd be
destroyed on every CI run.

Annotation yaml lives in a separate file, never overwritten by
re-capture. PNG XMP is purely machine-generated metadata.

### AD-04: Canvas editor writes annotation yaml, MDX editor writes MDX — neither writes both

The previous statement of this AD was "Annot editor never edits
MDX". That stance is correct for the **canvas editor**
(Phase 4 `<annot-screen-editor-modal>`): canvas-driven
annotation edits write only annotation yaml, never MDX. The
discarded DA-03 alternative — driving the legacy MDX `<Overlay>`
JSX from canvas operations via a byte-stable JSX writer —
remains rejected.

Phase 6 introduces a separate **MDX editor** surface
(`<annot-mdx-editor>`, MDXEditor-based) which does edit MDX,
but with a fundamentally different writer model: MDXEditor
parses MDX to AST, treats unknown JSX (`<AnnotFigure>`, etc.) as
opaque nodes preserved byte-stable, and serializes back
through Lexical's AST-grounded round-trip. There is no
"synthesize JSX from canvas operation" path; the MDX editor
edits MDX directly the way a user types into a text editor,
just with WYSIWYG presentation.

Two editors, two writers, one file kind each owns:

| Editor | Writes | Does NOT write |
|---|---|---|
| Canvas editor (Phase 4 `<annot-screen-editor-modal>`) | annotation yaml | MDX, PNG bytes, PNG XMP |
| MDX editor (Phase 6 `<annot-mdx-editor>`) | MDX | annotation yaml (delegates to canvas editor), PNG bytes, PNG XMP |

The MDX editor delegates annotation editing to the canvas
editor via image-click → `<annot-screen-editor-modal>`
(Phase 6b). Each writer owns one file kind end-to-end; no
writer touches two file kinds.

### AD-05: Match-anchored positions are first-class, free-coord is escape hatch

Match-anchored annotations survive UI layout changes. Free-coord
annotations break. The schema prefers match where possible:

- `rect` with `coversElements: [match, match]` — preferred
- `rect` with `bbox: { x, y, w, h }` — escape hatch

Editor UX (Phase 4) nudges users toward match-anchored
placements.

### AD-06: `overlays[]` and `annotations[]` are separate sections

`overlays[]` entries get a description rendered below the image
(via `<AnnotCallout for="id">` MDX JSX).

`annotations[]` entries are purely visual marking, no description
slot.

Split by **whether the docs flow renders a description slot for
it**, not by annotation kind. A numbered badge could in principle
be `kind: numberedBadge` under either section; the section
choice signals authoring intent.

### AD-07: Hook registry, not configurable fixture

Phase 0's relayer introduces module-level
`annotSourceResolvers` registry. Subsequent phases (2-5) add new
resolvers to this registry: MDX resolver (Phase 0), annotation
yaml resolver (Phase 2), free annotation resolver (Phase 3),
etc.

Single prototype patch, multiple contributors, tree-shake
friendly.

### AD-08: OSS / Cloud split via origin boundary (not iframe boundary)

Phase 5's editor lives at a **distinct origin** (annot-cloud's
domain — `annot.work` for the hosted variant,
`annot.example.com` for on-prem). The OSS side ships only the
`<AnnotEditButton>` component that routes visitors to that origin
via one of three embed modes (`newTab` default / `inline`
opt-in / `disabled`).

The boundary is **the origin separation**, not the iframe
specifically. Both `newTab` and `inline` modes preserve the same
guarantees:

- OSS docs sites stay lightweight (no bundled editor in either mode)
- annot-cloud is a clear paid service with its own infrastructure
- Security boundary is explicit at the origin level: GitHub credentials, OAuth state, GitHub App installation tokens never leak across origins
- On-prem deployments work cleanly: customer points `cloudUrl` at their own annot-cloud instance

An earlier iteration of this AD framed the boundary as
"iframe", which conflated the trust boundary (origin) with the
rendering mode (iframe vs new tab). The origin-boundary framing
is more accurate and admits the `newTab` default that better
fits Enterprise deployments. See **OQ-09** for the rationale
behind making `newTab` the default and `inline` an opt-in.

### AD-09: `ElementTree` is the canonical screen-capture model

A single Tier A `ElementTree` type in
`@ingcreators/annot-core/element-tree` represents "what's on
this page" across every capture source (browser extension,
Playwright, future Figma / screen recorder / OCR-derived).
Source-specific adapters convert raw outputs to ElementTree at
capture time. Downstream consumers (editor, Astro Image
Service, drift detector, annotation `match` resolver, MCP
tools) read only ElementTree.

This consolidates two previously parallel paths:

- Extension MAIN-world walker produced a flat `PageMetadata`
  list with role / name / bbox per element
- Playwright `ariaSnapshot({ mode: "ai", boxes: true })`
  produced a YAML tree with role / name / states / bbox / ref,
  parsed by a Playwright-specific `parseSnapshot` helper, with
  HTML attributes collected separately as a sibling
  `annot:attributes` YAML block

The two paths held the same information in incompatible shapes,
kept apart by implementation accident. Phase 1 of this roadmap
replaces both with ElementTree. PRODUCT_DIRECTION P5 is rewritten
to reflect the new canonical model.

Key shape decisions:

- **Tree, not flat list.** Reflects DOM parent-child relationships and matches what consumers (editor sidebar, drift detector subtree comparison) naturally want.
- **`ref` is required, `e<n>` format.** Stable within one capture; not stable across re-captures (drift detection uses `match: { role, name }` for cross-capture identity — see OQ-11).
- **`states` is a string array, not a brackets-merged token blob.** Cleanly separable for diff: today Playwright's YAML mixes `[active] [ref=e21] [box=...]` in one bracket group; the ElementTree separates them.
- **`attributes` lives on each node**, eliminating the parallel `annot:attributes` YAML. The single tree carries all the per-element data.

The user authorized breaking `PageMetadata` to make this
consolidation possible. Phase 1's first three sub-phases land
as a single PR because the schema break is atomic.

### AD-10: React permitted inside `<annot-mdx-editor>` boundary; Lit elsewhere

MDXEditor (Phase 6's MDX WYSIWYG) is React-based, while
`@ingcreators/annot-host-ui` is otherwise Lit-only. Mixing the
two is allowed under a strict containment rule:

- `react`, `react-dom`, and React-only Lexical / MDXEditor packages MAY be imported from `packages/host-ui/src/annot-mdx-editor.ts` and from sibling files under `packages/host-ui/src/mdx-descriptors/` and `packages/host-ui/src/mdx-editor-internal/`.
- No other host-ui file imports React. The boundary is CI-enforced by extending `packages/host-ui/host-boundary.test.ts` with a probe that walks `require.cache` after importing each non-`annot-mdx-editor` host-ui entry and fails if any `react` / `react-dom` / `@mdxeditor/*` module appears.
- Plugin authors writing custom Annot UI continue to use Lit (the `@ingcreators/annot-web/lit` re-export). React is not a public extension surface — the MDX descriptors are first-party only at the time of Phase 6 landing.

The trade-off: ~500 KB gzipped of bundle weight in editor-mode-only
code paths. Acceptable because the MDX editor is opt-in per
file kind and lazy-loaded — pages that don't open `.annot.mdx`
files never pay the cost. The host-ui Lit consumers (PWA
editor surface, VSCode `.annot.png` custom editor, etc.) stay
unaffected.

The previous Lit-only invariant ("the host-ui surface is Lit;
no other UI framework") is intentionally narrowed by AD-10
from "no other framework ever" to "no other framework outside
`<annot-mdx-editor>`'s boundary". The original invariant was
guarding against accidental framework proliferation, not
guarding against deliberate opt-in within a tightly-bounded
component.

### AD-11: MDXEditor chosen over Tiptap, Lexical raw, ProseMirror raw, CodeMirror split-view

Phase 6's WYSIWYG MDX editor MUST: parse MDX (not patched
markdown), preserve unknown JSX byte-stable, allow registered
JSX components to render with custom WYSIWYG renderers,
support frontmatter and imports, and round-trip the AST
without normalizing unrelated content.

Only MDXEditor meets all five out of the box. Alternatives
evaluated:

| Candidate | MDX first-class | Unknown JSX preserved | Custom JSX renderers | Frontmatter | Round-trip safety | React dep |
|---|---|---|---|---|---|---|
| **MDXEditor** | ✓ | ✓ (AST opaque nodes) | ✓ (`jsxComponentDescriptors`) | ✓ | ✓ (Lexical AST) | yes |
| Tiptap (ProseMirror) | ✗ (markdown ext only) | needs custom serializer | needs custom NodeView | needs custom node | ⚠️ (formatting loss risk) | no |
| Lexical raw | ✗ | needs custom plugins | needs custom node | needs custom plugin | ✓ once plugins built | no |
| ProseMirror raw | ✗ | needs custom schema | needs custom NodeSpec | needs custom plugin | ⚠️ (formatting loss risk) | no |
| CodeMirror 6 + lezer-mdx | ✓ (source-as-truth) | ✓ (source bytes) | n/a (not WYSIWYG) | ✓ | ✓ (no transform) | no |

CodeMirror is the only non-React candidate that passes the
correctness rows. It fails the UX requirement (WYSIWYG) — it's
a source-pane editor, not a rich-text editor. It's held in
reserve as a fallback if MDXEditor proves unworkable in
practice but is not the Phase 6 baseline.

Tiptap / Lexical raw / ProseMirror raw each require
re-implementing what MDXEditor already provides. Estimated 2-4x
the implementation cost with no advantage at the end. Adopting
Lexical raw and re-implementing the MDX plugin set is
particularly wasteful given that `@mdxeditor/editor` IS that
plugin set, packaged.

The single trade-off is the React dep captured in AD-10. The
roadmap accepts that trade-off in exchange for implementation
savings + the maturity of MDXEditor's AST round-trip.

### AD-12: Card-style docs and screen-spec docs share one authoring path

Card-style docs (today's `@ingcreators/annot-doc` block format)
and screen-spec docs (today's MDX with `<AnnotFigure>` /
`<AnnotCallout>`) are conceptually the same: an authored
document referencing one or more annotated images, with text
describing what's in the images, intended for distribution
to humans. The visual layout differs (card grid with steps vs.
screen-per-page with numbered callouts) but the underlying
data model is identical.

Phase 8 collapses them onto a single authoring path:

- **One file format**: `.annot.mdx` for everything. The
  `.annot.doc.html` block format is removed in Phase 8d.
- **One editor**: `<annot-mdx-editor>` (Phase 6) for both
  card-flavored and spec-flavored authoring.
- **One output adapter**: `@ingcreators/annot-product-docs-html`
  (Phase 7) emits single HTML for both.
- **Two JSX component families** distinguish style:
  - Card flavor: `<AnnotCardDoc>` + `<AnnotCardStep>`
  - Spec flavor: `<AnnotFigure>` + `<AnnotCallout>`

There is no frontmatter `type` field to lock the document into
one style; the JSX usage in the MDX body determines style.
Hybrid documents (cards + spec figures mixed) are mechanically
supported even if the wizard doesn't stamp them.

This unification eliminates significant duplicated surface
area — two editors, two storage formats, two test surfaces,
two export pipelines — that previously existed only because
the two doc styles evolved separately.

### AD-14: Annot's public MDX components use the `Annot` prefix

All MDX components published by Annot use a PascalCase
`Annot` prefix in their JSX tag name:

- `<AnnotFigure>` (was `<Screen>` in early drafts)
- `<AnnotCallout>` (was `<Description>` / inherits from legacy `<Overlay>`)
- `<AnnotCardDoc>` / `<AnnotCardStep>` (new in Phase 8)
- `<AnnotEditButton>` (was `<EditButton>`)
- `<AnnotFigureList>` (was `<ScreenList>`)
- `<AnnotHistoryEntry>` (was `<HistoryEntry>`)
- `<AnnotTransition>` / `<AnnotTransitionGraph>` / `<AnnotTransitionTable>` (was `<Transition>` family)

Rationale:

1. **Zero collision risk**. shadcn / Mantine / Chakra / Radix
   and other UI library ecosystems heavily use generic
   sub-component names like `Description`, `Card`, `Caption`,
   etc. MDX consumers routinely import these alongside Annot
   components; the `Annot` prefix prevents naming conflicts
   without forcing import aliasing.
2. **Consistency with Lit conventions**. Annot's built-in Lit
   web components already use the `annot-` prefix
   (`<annot-mdx-editor>`, `<annot-screen-editor-modal>`,
   `<annot-create-document-wizard>`, etc.). The MDX-side
   `Annot` PascalCase prefix mirrors that convention in JSX.
3. **Grep-friendly ownership**. Searching for `AnnotXxx` across
   a docs repo instantly surfaces every Annot integration
   point in MDX bodies.
4. **Semantic precision**. The original `<Screen>` name
   implied UI screens specifically; the rename to
   `<AnnotFigure>` admits diagrams / photos / mockups / charts
   under the same authoring component.

Verbose for some authors. Two escape hatches:

- MDX import aliasing: `import { AnnotFigure as Figure, AnnotCallout as C } from "@ingcreators/annot-product-docs-astro/components";`
- Astro auto-import config in `astro.config.mjs` to inject the components without explicit imports — a future ergonomic helper if requested.

Phase 7a executes the rename across the existing seven
production .astro components + `<EditButton>` plan additions
+ Phase 6's descriptor registry. A migration codemod
(`annot-docs rename-jsx-components`) updates downstream
MDX consumers.

## Open Questions

### OQ-01: Annotation yaml schema versioning policy

`version: 1` is in the schema, but the policy for v2 / v3 is
open:

- **(a) Strict version dispatch**: parser reads `version`, picks code path. Old code refuses new versions.
- **(b) Best-effort forward compat**: parser ignores unknown fields, processes known ones. Old code partially handles new versions.

**Recommended:** (a) for the v1 → v2 transition (likely breaking
shape changes); (b) within a major version (e.g. v1.0 → v1.1
adds optional fields).

### OQ-02: Multi-book overlay sets — same annotation, different audience

workflow-app's operation-manual and screen-design books point
the same `login.png` at different `<AnnotCallout>` content.

Two options:

- **(a) Single annotation yaml shared between books, descriptions diverge** — both books use the same `login.annotations.yaml`, each MDX file has its own `<AnnotCallout>` set.
- **(b) Per-book annotation yaml** — `login.OM.yaml`, `login.SD.yaml`. Allows different numbering / different intent per book.

**Recommended:** (a). Audience differences are in description
text, not visual marking. Shared yaml encourages consistency.
If a book genuinely needs different overlays (different
elements highlighted), it gets its own yaml.

### OQ-03: i18n match key strategy

For multilingual UIs, the snapshot is per-language (aria names
differ). So `match: { role, name }` differs per language.

Options:

- **(a) Full per-language duplication** — separate yaml per language
- **(b) data-testid based matching** — `match: { testId: "email-input" }` is language-stable. Requires app discipline (testids on every overlay target).
- **(c) Reference-based matching** — uses snapshot `[ref=eN]` markers. Brittle (refs change across captures).

**Recommended:** (a) as default, (b) as opt-in for projects with
testid discipline. (c) not supported.

### OQ-04: Editor mode — general PNG annotator vs spec-authoring

Annot editor today is positioned as a general PNG annotation
tool. Phase 4 adds the Overlay tool which is spec-specific.

When opening an arbitrary PNG (no linked annotation yaml), the
Overlay tool is irrelevant. Options:

- **(a) Always show Overlay tool, disabled if no snapshot**
- **(b) Mode toggle in UI** — "PNG annotation" vs "Screen spec authoring"
- **(c) Auto-detect** — show Overlay tool when PNG XMP has snapshot AND linked yaml is loadable

**Recommended:** (c). Reduces UX friction for general PNG annotators while exposing the docs flow when context permits.

### OQ-05: PR-mode vs direct-push for GitHub round-trip

Phase 5's commit policy:

- **(a) PR-mode** — every edit creates a PR. Safe (review gate) but high friction (many small PRs).
- **(b) Direct push** — edits go straight to main. Fast but unsafe for production docs.
- **(c) Per-installation policy** — repo admin configures in annot-cloud dashboard.

**Recommended:** (c). Default to PR-mode for installations on
public repos; allow direct-push for solo / trusted-team repos.

### OQ-06: Embedded editor read-only mode for unauthenticated visitors

When a visitor without GitHub write access clicks Edit:

- **(a) Disabled button** — can't edit, button greyed out
- **(b) Read-only editor** — editor opens, shows annotations, but can't save
- **(c) PR suggestion flow** — fork repo + commit + PR

**Recommended:** (b) + a "Suggest changes" CTA that leads to (c).
Combines preview value with contribution path.

### OQ-07: Real-time collaboration scope

If multiple editors open the same yaml simultaneously:

- **(a) Last-write-wins** — simple, occasional data loss
- **(b) Optimistic locking** — GitHub ETags prevent overwrites, second writer sees conflict
- **(c) CRDT-based collab** — real-time merge, no conflicts ever (high implementation cost)

**Recommended:** (a) for v1, (b) for v1.1. (c) deferred
indefinitely.

### OQ-08: When does the legacy `<Overlay>` JSX support actually get removed?

Phase 2 dual-supports legacy `<Overlay>` JSX and the new
`<AnnotCallout for>` form. When does the legacy form get deleted?

- **(a) Hard deprecate immediately**: bump major version, drop in next major
- **(b) Soft deprecate for 2-3 release cycles**: warning at build time, drop later
- **(c) Permanent dual support**: never drop, both forms work

**Recommended:** (b). Two cycles (~3 months) of dual support
with build warnings gives external consumers time to migrate
without permanent maintenance debt.

### OQ-09: `<AnnotEditButton>` embed mode — `newTab` default vs `inline` default

Phase 5's `<AnnotEditButton>` component routes visitors to
annot-cloud via either `newTab` (open editor in new tab) or
`inline` (modal iframe). The default mode affects how Phase 5
plays with Enterprise constraints.

Options:

- **(a) `newTab` default, `inline` as opt-in.** Click opens new tab; modal iframe available via `mode="inline"` prop.
- **(b) `inline` default, `newTab` as opt-in.** Click opens modal iframe; new tab available via `mode="newTab"` prop.
- **(c) No default — author must explicitly set `mode`.** Forces a decision per call site.

**Recommended:** (a).

This was originally framed as a UX preference (in-page vs tab
switching), and an earlier draft of this roadmap leaned toward
(b) for the "stays in context" feel. Re-evaluation surfaced
that `inline` mode interacts badly with Enterprise constraints:

| Constraint | `inline` (iframe) | `newTab` |
|---|---|---|
| Strict CSP `frame-src` | ✗ requires per-customer whitelisting | ✓ unaffected |
| Third-party cookies (Safari ITP / Brave / corp Chrome) | ✗ OAuth session breaks | ✓ unaffected |
| SAML / Okta / Azure AD SSO redirect | ✗ frame-busting IdPs reject iframe redirect | ✓ native flow works |
| On-prem `cloudUrl` deployments | ✗ docs site must know iframe target at build time | ✓ link target is just a config string |
| Network isolation / air-gapped | ✗ iframe fails if annot-cloud unreachable | ✓ same, but link can target on-prem cloud |
| Audit log capture by customer | ✗ postMessage-bridged events are awkward | ✓ all activity on annot-cloud origin, log natively |
| Long-running edit sessions | ✗ parent navigation kills iframe | ✓ new tab is independent lifecycle |
| Visual continuity / brand consistency | ✓ stays on docs site | ✗ visible context switch |
| Initial discovery / ease | ✓ "feels seamless" | ✗ "tab switching" is a learnable extra step |

Eight of nine rows favor `newTab`. Only the bottom two favor
`inline`, and they're consumer-UX concerns rather than
deployment-correctness concerns. For a product positioned to
serve both consumer (Pro tier) and Enterprise tiers from the
same OSS component, **`newTab` as the safe default + `inline`
as a deliberate consumer opt-in** is the right shape.

Enterprise tier (per `annot-cloud-roadmap.md`) effectively
**disables `inline` mode** to enforce the deployment-correctness
guarantees. The OSS component still ships both modes; Enterprise
config (`embedMode: "newTab"` enforced server-side) gates the
choice.

### OQ-10: ElementTree canonical serialization — YAML or JSON?

Phase 1d stores ElementTree in PNG XMP. Two serialization
candidates:

- **(a) YAML** — `compressionFlag=1` (deflate) keeps size manageable. Human-readable when manually inspecting PNG XMP via `exiftool -annot:elementTree login.png`. Matches today's Playwright `ariaSnapshot` aesthetic. Whitespace-sensitive parsing.
- **(b) JSON** — More compact (no indentation overhead). Parse-efficient. Unambiguous. Less human-readable in raw form.
- **(c) Both, selectable** — Writer defaults to YAML; reader accepts both. Allows JSON-preferring tools without forcing YAML on every consumer.

**Recommended:** (a) YAML as the canonical wire format, with
`@ingcreators/annot-core/element-tree/yaml.ts` as the
authoritative serializer.

Reasons:

1. **Human-readability matters for debug**: PNG XMP gets
   inspected via tools (`exiftool`, our own `annot show-xmp`
   CLI). YAML is readable; JSON in raw form is wall-of-text.
2. **Diff-friendly via git textconv hook**: a future
   `git diff --textconv` for `.png` files that extracts the
   ElementTree benefits from line-based YAML over
   pretty-printed JSON.
3. **Compression evens out the size difference**: ElementTree
   YAML has high token repetition (role / name / bbox keys);
   deflate compresses it well. The raw-size delta against JSON
   is small post-compression.
4. **Parse cost is negligible**: ElementTree per page is
   ~1-50 KB. YAML parsing at this scale is sub-millisecond
   even in Node.

JSON is still exported by the serializer module
(`serializeElementTreeToJson`) for callers who want it
(MCP tool payloads, AI agent prompts, in-memory snapshotting).
Just not the on-disk canonical.

### OQ-11: `ref` stability across re-captures

ElementTree's `ref: "e<n>"` is depth-first-counted at capture
time. Re-running the capture produces the same numbering for a
structurally-identical page, but adding or removing a single
element shifts every ref after it. This makes ref unsuitable
as a cross-capture identity for annotations.

Options for cross-capture identity:

- **(a) Accept ref as transient.** Annotation yaml's `match: { role, name }` is the cross-capture identity. Ref is only meaningful within a single ElementTree instance.
- **(b) Anchor refs to (role, name, parent-path).** Compute ref as a hash of the element's accessibility location. Stable across captures iff the element's role / name / DOM position is stable.
- **(c) Carry stable IDs from the page itself.** Use HTML `id` / `data-testid` / `data-annot-id` attributes when present. Falls back to (a) when absent.

**Recommended:** (a) for v1.

Reasons:

1. **Annotation yaml already uses `match`**: the cross-capture identity problem is solved at the annotation layer. Adding a parallel cross-capture identity in ElementTree is over-engineering.
2. **(b) is brittle in practice**: name-based hashes break on translation (i18n), on small UI text changes (".. submit" → "... submit"), and on accessible-name resolution differences across browsers.
3. **(c) is good but additive**: a future Phase 2.5 could add `stableId?: string` to ElementNode as an opt-in for pages with `data-testid` discipline. Doesn't conflict with (a).

Drift detection works against `match` lookups, not ref. The ref's
job is purely "address this node within this tree" — sufficient
for the editor's hotspot rendering and within-capture diagnostics.

### OQ-12: Phase 6 first host — VSCode vs annot.work/app vs Annot desktop

Phase 6's `<annot-mdx-editor>` needs a first host platform.
The component is host-neutral by design, but one of the three
realizations (6d / 6e / 6f) lands first.

- **(a) VSCode first (6d)** — fastest dogfooding loop. Most workflow-app contributors already author `.mdx` in VSCode. Smallest install surface (just an extension update). Reuses the existing `.annot.{svg,png,jpeg,jpg}` custom-editor registration pattern.
- **(b) annot.work/app first (6e)** — broadest reach, no IDE requirement. Verifies the hosted Phase 5 ↔ Phase 6 integration end-to-end early. Larger surface (gallery routing, file open dialog, etc.).
- **(c) Annot desktop first (6f)** — local file editing, no web hosting concerns. Smallest deployment risk. But the desktop host has fewer current users than VSCode or the web.

**Recommended:** (a). VSCode is where the existing workflow-app
contributors author MDX today, so the dogfooding loop is
fastest and most honest. annot.work/app (b) follows once the
editor proves out; desktop (c) comes essentially for free
thereafter (Annot desktop already loads host-ui Lit
components).

### OQ-13: MDXEditor descriptor scope — first-party only vs. plugin API

Phase 6c lands descriptors for Annot's first-party
product-docs JSX (`<AnnotFigure>` / `<AnnotCallout>` / `<AnnotEditButton>` /
etc.). Custom components added by docs authors (e.g.
`<Note>`, `<KeyboardKey>` mentioned in AD-02) are NOT
descriptor-registered out of the box.

Options:

- **(a) First-party only** — non-registered JSX renders as opaque "MDX block: <ComponentName>" placeholder. Docs authors edit such blocks via the source view. (Phase 6's baseline.)
- **(b) Configurable descriptor registry in `annot-docs.config.ts`** — docs authors register their own components for WYSIWYG rendering. Requires a public descriptor API + version stability commitment.
- **(c) Best-effort generic descriptor** — heuristically renders any unknown JSX as a "block with children" with toolbar for inserting/editing children. Risky; could mislead authors about what's actually being preserved.

**Recommended:** (a) for Phase 6 landing. (b) as a Phase 6.x
follow-up once descriptor API stabilizes (descriptor shape is
likely to iterate during 6c, so freezing the public API at
6c-landing time is premature). (c) not pursued — opaque
preservation is safer than wrong WYSIWYG.

## Discarded alternatives

### DA-01: PNG XMP carries everything (single-file vision)

**Idea**: Image + snapshot + annotations + overlay text all in
PNG XMP. MDX becomes optional, Astro reads everything from PNG.

**Fatal flaw**: Re-capture overwrites PNG. Every CI run destroys
human-edited overlay data. Sidecar `.overlays.yaml` was
proposed as mitigation, but sidecar fragility (move PNG without
yaml → data lost) is just as bad.

### DA-02: Sidecar yaml paired with PNG by filename

**Idea**: `login.png` + `login.overlays.yaml` in same directory.
Convention-based pairing.

**Fatal flaw**: Filesystem operations break the pair silently.
`mv login.png` doesn't bring the yaml. Slack-shared PNG
arrives without yaml. No build-time validation.

### DA-03: PNG snapshot + MDX inline overlays + JSX writer

**Idea**: Snapshot in PNG XMP; overlays stay as legacy `<Overlay>`
JSX in MDX; Annot editor writes MDX directly via byte-stable JSX
rewriter.

**Fatal flaw**: MDX JSX writer is the hardest single component
in the whole architecture. remark-mdx doesn't preserve
formatting on serialization; achieving byte-stability across
insertion / deletion / reordering of JSX nodes is a multi-week
implementation that consumers (anyone writing MDX) would
notice and dislike (their carefully formatted MDX gets
reformatted by the tool).

**Partial reversal in Phase 6**: Phase 6's MDX editor does
write MDX, but the fatal-flaw analysis above doesn't apply
because it doesn't *synthesize JSX from canvas operations* —
the user types into a WYSIWYG editor whose AST round-trip is
grounded in MDXEditor's Lexical model. Unknown JSX is
preserved opaque (not reformatted); registered JSX nodes
serialize via per-descriptor rules. The Phase 4 canvas editor
still doesn't write MDX (AD-04 maintains the canvas/MDX
writer split). DA-03's specific failure mode — a canvas
operation needing to emit JSX bytes — is still off the table.

### DA-04: Two yaml files (annotation + description)

**Idea**: Annotation in `.annotations.yaml`, description in
`.descriptions.yaml`. MDX references both.

**Fatal flaw**: Description text wants markdown formatting,
inline JSX (`<Link>`, `<code>`, `<Note>`), multi-paragraph
structure. YAML strings are awkward for all of these. MDX is
the right home for description body.

### DA-05: PNG-driven editor that writes both PNG XMP and MDX JSX

**Idea**: Editor writes annotations to PNG XMP AND writes
legacy `<Overlay>` JSX to MDX. Bidirectional sync.

**Fatal flaw**: Combines DA-01's re-capture problem with DA-03's
JSX writer cost. Sync direction ambiguity (which is the source
of truth?) creates race conditions.

### DA-06: Card document remains a separate format alongside MDX docs

**Idea**: Keep `@ingcreators/annot-doc`'s block-based document
format (`.annot.doc.html`) as a distinct authoring path,
alongside MDX-based screen-spec docs. Share themes via the
AD-12 of an earlier draft (theme registry shared, authoring
paths distinct). Card-document users continue editing via
`<annot-doc-shell>`; spec-document users edit via `<annot-mdx-editor>`.

**Fatal flaw**: The same "screen + annotation + description"
data lives in two authoring paths, two storage formats, two
export pipelines, two test surfaces. Doubles the maintenance
burden with zero functional advantage — every feature added
to one side eventually wants the other side to match.
Furthermore, file-manager UX must present two "Create
document" actions; users must understand the difference
before authoring. The block-based editor's UX strengths
(direct drag-to-reorder, inline image click) can be matched
in MDXEditor via custom Lexical descriptors (Phase 8a), so
there's no compelling capability gap that justifies the
duplication.

The user explicitly confirmed (2026-05-22 session) that the
unpublished `annot-doc` package can be destructively removed.

### DA-07: Generic JSX names (`<Screen>` / `<Description>` / etc.) without `Annot` prefix

**Idea**: Publish Annot's MDX components with concise generic
names — `<Screen>` for the figure, `<Description>` for the
callout body, `<Card>` / `<Step>` / `<EditButton>` / etc.

**Fatal flaw**: Naming collisions with the broader MDX
ecosystem. shadcn / Mantine / Chakra / Radix and similar UI
libraries heavily use generic sub-component names like
`Description` (every Card / Dialog / Sheet / Menu / Tooltip
component in shadcn ships a `Description` sub-component).
MDX consumers routinely import these alongside Annot
components; collision is the rule, not the exception. React
Native projects writing docs in MDX further collide on
`Screen` (React Navigation's `Stack.Screen`). The semantic
narrowness of `Screen` itself is also a problem — it implies
UI screens, excluding figures / diagrams / photos / charts
that Annot equally supports.

AD-14 captures the resolution: `Annot` prefix on every
public MDX component, zero collisions guaranteed.

### DA-08: Frontmatter `type` field categorizing card vs spec

**Idea**: Add `type: card-doc` or `type: screen-spec`
(or `type: book`, etc.) to the MDX frontmatter to declaratively
categorize each document. file-manager / editor / HTML adapter
inspect the `type` field to render category-specific affordances.

**Fatal flaw**: The `type` field duplicates information already
present in the MDX body — the JSX usage pattern
(`<AnnotCardDoc>` vs `<AnnotFigure>` as top-level) inherently
determines the category. A `type` field can drift out of sync
with the body, producing ambiguous state. Hybrid documents
(cards + figures mixed) can't be expressed as a single `type`
value. file-manager category detection works fine via a
cheap-parse of the first top-level JSX element.

AD-12 captures the resolution: no `type` field; category
emerges from JSX usage.
